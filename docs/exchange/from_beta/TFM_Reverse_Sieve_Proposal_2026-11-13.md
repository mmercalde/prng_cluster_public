# TFM reverse sieve: proposed correction and consequences of leaving it unchanged

**For:** Michael and Team Alpha  
**From:** Team Beta  
**Date:** November 13, 2026  
**Status:** Design proposal for discussion; no implementation or deployment authorized by this document.  
**Source reviewed:** Public mirror `mmercalde/prng_cluster_public` at `b10e1ef1bebfd4656f95f48df25410a993e88d63`. Live VM101 and private-repository parity are unverified.

## 1. Recommendation

Correct the comparison of observations to generator positions. Keep generation forward-only, retain a population of approximate survivors, and preserve the downstream TFM workflow. Do not silently substitute a second observation window and call that a repair of the original design.

There are two separate questions:

1. **Correctness:** Does a candidate trajectory that reproduces the observation window survive validation from either end?
2. **Additional filtering:** Does the second pass introduce constraints that supply additional evidence?

The first can be repaired. The second requires an explicit construction and evidence; reversing the order of the same comparisons does not make them statistically independent.

This proposal is a correction contract and a staged implementation plan. It is not yet a complete, performance-qualified hybrid kernel design. Beta's earlier buffer description should not have been presented as if it settled that engineering work.

## 2. What is established

The active worker reverses observation values for reverse families (`miner/range_miner_worker.py:1200-1205`). The Java LCG constant reverse kernel starts from the candidate seed, advances forward, and compares its next output with the next item in that reversed list (`prng_registry.py:3131-3155`). It does not restore the observation's original generator position.

The final directional intersection uses numeric seed keys (`utils/canonical_records.py:209-211`). Thus a candidate missing from reverse is excluded regardless of its forward score.

The earlier local review executed the four unchanged Java LCG kernel bodies through a single-thread CPU wrapper. For a 12-draw stream generated by raw seed 1,234,567 at skip 9:

| Comparison | Forward | Reverse with flipped observations |
|---|---:|---:|
| Constant skip, searched at skip 9 | 12/12 | 0/12 |
| Constant skip, search 9–30 | 12/12 | 1/12 |
| Hybrid kernels, same constant-gap stream | 12/12 | 1/12 |
| Hybrid kernels, separate variable-gap stream | 12/12 | 1/12 |

The variable gaps were `[5,6,4,7,5,3,8,5,6,4,7,5]`. Hybrid diagnostic settings were tolerance 10 and maximum consecutive misses 20. Both reverse bodies scored 12/12 on the applicable streams when supplied chronological targets directly. These are bounded CPU observations, not GPU or fleet certification. The broader seed-count experiments in Alpha's brief were not repeated.

This establishes loss of guaranteed retention. It does not establish that every generating candidate is rejected, that every survivor is noise, or that all historical predictions are invalid.

## 3. Required comparison contract

For observation index `i`, preserve the pair:

**observation D[i] ↔ generated output at position p[i].**

Forward visits those pairs oldest-to-newest. Reverse visits them newest-to-oldest. Neither direction changes the pairings. The PRNG itself always advances forward.

Both passes must agree on seed meaning, generator parameters, initial phase, observation ordering and output projection. The existing three residue checks and tunable thresholds can remain. A known generating candidate is a positive control for this contract, not a demand that TFM recover a unique historical seed.

### Constant skip

With zero-based observation indices and skip `q`, the current burn convention gives:

`p[i] = phase + (i+1)*(q+1)`.

For each candidate and searched skip:

1. Generate the needed outputs forward using the same seed and phase as forward validation.
2. Retain the selected outputs with their indices, or use forward replay/checkpoints that reproduce them.
3. Compare `D[k-1]` with output `p[k-1]`, then descend through the correctly paired positions.
4. Compute the match rate, apply the reverse threshold, and retain the winning hypothesis under a specified tie rule.

The implementation design must bound memory and replay cost. A buffer for every seed across the full fleet is not prescribed; use a bounded batch or per-candidate strategy. Kernel ABI, occupancy and throughput effects require review before implementation.

**Expected result:** For the same fixed trajectory, forward and reverse count exactly the same matches. If both search the same skip range and maximize the same score, the best rates also agree. Equal thresholds then produce identical constant-mode survivor sets; unequal thresholds reduce the intersection to the stricter threshold. This repairs the pairing but does not preserve the old reduction in survivor count.

### Variable skip / hybrid

Represent a hypothesis as chronological output positions, or equivalently a gap sequence with:

`p[0] = phase + q[0] + 1`, and `p[i] = p[i-1] + q[i] + 1`.

Reverse search examines possible positions from newest to oldest in a stream generated forward. Every accepted path must obey the agreed gap rules and connect back to the same initial seed/phase. A missed observation still occupies a position in that path; it must not silently erase a draw or reset the trajectory.

Before coding, Alpha's design must specify:

- The admissible gap bounds and how strategies constrain them.
- How the newest possible position is bounded and how initial alignment is checked.
- Whether each pass searches the same path space or uses a documented approximation.
- Branching, backtracking, pruning, score maximization, tie handling and miss/abort rules.
- Memory limits and behavior when a search budget is exhausted. An incomplete search must be distinguished from an exhaustive finding of no valid path.

**Do not claim a retention guarantee from a greedy search that can discard the admissible generating path.** Merely storing the forward pass's single winning path and replaying it backward is a valid consistency check of that path, but not an independent search from the newest observation.

The current hybrid algorithms differ: forward recentres a skip estimate (`prng_registry.py:1027-1048`); reverse searches from zero through tolerance (`:3200-3204`). They also select strategies differently (`:1060-1067`, `:3229-3239`). Removing the host flip alone does not resolve those semantics.

## 4. Comparison with Alpha's proposals

| Construction | What it changes | What it establishes | Limitation |
|---|---|---|---|
| Leave current implementation | Nothing | Candidate matches under the existing original-order and reversed-target predicates | Does not guarantee preservation of a correctly generating chronological trajectory |
| Alpha A / Beta position-preserving construction | Restore each draw/output pairing on the same window | Correct forward-only validation of those observation positions | Same fixed trajectory gives the same total match count in either order |
| Alpha B | Use a second, adjacent newer stretch with consistent continuation | Additional observation constraints, if implemented coherently | Changes the observation scope; independence and benefit are not automatic |

For B, specify which data form each stretch, the shared seed origin and trajectory, behavior when no newer observations exist, and separation from ML evaluation data. Any observations used by either sieve are selection data, not untouched holdout data.

Current RANGE-MINER policy pins generator phase to zero (`miner/range_miner_worker.py:601-625`); Java forward hybrid has no phase argument (`prng_registry.py:1007-1012`). B therefore needs an explicit implementation route rather than an assumed offset change. Advancing a seed on the host also requires preserving original candidate identity for the intersection.

For any construction, `P(F and R) = P(F) * P(R given F)`. Substituting `P(R)` for the conditional probability needs support. A squared-odds claim is not a consequence of having two passes. TFM also does not require a unique survivor.

## 5. What happens if we keep the sieves as they are?

**The software can continue producing survivors and feeding ML. The demonstrated issue concerns which candidates it selects and what those selections mean.**

| Consequence | Assessment |
|---|---|
| Correctly generating candidates can be discarded | Confirmed by source and bounded local checks. Rate depends on observations, thresholds, skip search and strategy. |
| Small intersections continue to occur | A reduction in counts demonstrates filtering, not that retained candidates have stronger chronological consistency or predictive value. |
| ML receives the existing selected population | It learns from candidates admitted by the two current predicates. It cannot restore a discarded candidate to that input population, although other candidates could still carry useful information. |
| Current reverse scores retain a numerical meaning | They measure agreement under the flipped-target algorithm. They should not be interpreted as correctly positioned backward validation. |
| Prior infrastructure and test work remain useful | Scheduling, CUDA/ROCm operation, marshalling, artifact integrity and tests of the implemented semantics are separate from this design mismatch. Their evidence retains its actual scope. |
| Prediction performance is uncertain | This review neither proves nor disproves useful out-of-sample performance. A functional-mimicry heuristic can be empirically useful without reproducing a historical generator. That usefulness must be demonstrated on data untouched by selection and tuning. |
| More computation does not fix the pairing | A larger sweep explores the same predicate. It may produce more survivors without addressing this mismatch. |
| Claims of “real rather than noise” or squared filtering odds remain unsupported by this mechanism alone | The observed intersection cannot establish those interpretations. |

Keeping the current algorithm as a **documented empirical baseline** is a defensible research choice. Keeping it while continuing to describe it as position-preserving reverse validation is not supported by the reviewed source. Neither the defect nor an eventual fix alone establishes which version predicts better.

No live run needs to be halted by this document. Preserve existing results and configurations; do not delete historical artifacts or silently relabel them as outputs of a corrected sieve.

## 6. Smallest practical implementation and comparison plan

1. **Alpha writes one reconciled design.** Use the pairing contract above and state separately whether additional observations are intended. Resolve the original PDFs before calling the design faithful to their complete specification.
2. **Build a bounded reference for the proposed semantics.** Keep production unchanged. For constant mode, establish the expected equality of directional match counts. For hybrid, define and verify the admissible path space before claiming guaranteed retention.
3. **Implement an explicitly versioned experimental path.** Preserve candidate attribution and downstream contracts where feasible. If meanings, required provenance or output fields change, document/version that change rather than hiding it behind unchanged array shapes.
4. **Verify the changed behavior narrowly.** One chronological dataset and one candidate through both directional passes and the actual intersection. Cover nonzero constant skips, variable gaps, threshold boundaries and deliberately broken pairings. GPU execution checks follow the reference checks; no full foundational fleet campaign is prescribed.
5. **Compare current and proposed behavior on the same bounded inputs.** Record retained candidates, directional scores, path consistency, runtime and memory. Do not tune thresholds solely to reproduce the old intersection size; that would not demonstrate correctness.
6. **Evaluate predictive usefulness separately.** Compare existing, corrected and any B variant against a stated baseline on evaluation data untouched by sieve selection, training and tuning. Archive the exact algorithm version and data boundaries.

Acceptance requires: correct position pairing, preservation of admissible positive controls within the specified search scope, bounded resource behavior, faithful integration and honest score meanings. Whether to adopt A, develop B or retain the old heuristic is Michael's decision after the comparison. No adoption or code change has occurred here.
